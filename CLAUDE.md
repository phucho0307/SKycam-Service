# Claude Code notes for this repo

## Stack

- Backend: Rust workspace, Rocket 0.5, official `mongodb` driver, tokio runtime.
- Frontend: Vite + React 19 + TypeScript + Tailwind v4 (CSS-based config).
- Infra: MicroK8s on VPS (`obsserv@10.101.229.77`), Traefik ingress (MicroK8s default; IngressClass `public` is registered by Traefik), Cloudflare Tunnel terminating at Cloudflare's edge (Mode A while behind NAT; switches to Origin Cert + direct DNS for colo move — see `infra/cloudflare/README.md`).
- GitOps: ArgoCD on the cluster, app-of-apps pattern, three env Applications + cloudflare-tunnel Application.
- Secrets: Sealed Secrets controller; everything encrypted in git.
- CI/CD: GitHub Actions → GHCR images → workflow bumps kustomize image tag in the matching overlay → ArgoCD syncs.

## Conventions

- Workspace crates live under `backend/crates/<name>`.
- Each backend crate has its own binary and its own k8s Deployment.
- Frontend pages live in `frontend/src/routes/`, components in `frontend/src/components/`.
- All env-driven config goes through `crates/api/src/config.rs` (and equivalents per crate). Do not read env vars inline elsewhere.
- Domain types shared between crates live in `crates/domain`.

## Environments and branches

- `dev` branch → `dev.observatory.services` → namespace `observatory-dev` (ArgoCD auto-sync)
- `release` branch → `release.observatory.services` → namespace `observatory-release` (ArgoCD auto-sync)
- `main` branch → `observatory.services` → namespace `observatory-prod` (ArgoCD manual sync)

Never merge to `main` directly; promote through `dev` → `release` → `main`.

GitHub org slug is `ObservatoryServices`. GHCR is case-insensitive but image refs MUST use lowercase `observatoryservices`.

## Avoid

- Postgres / SQL **in the current Rust codebase** — what's shipped is MongoDB only. (Postgres *is* planned for the Go ingest rebuild + auth/RBAC — see `GO_GRPC_AND_POSTGRES.md`. Don't introduce it into the existing Rust services ahead of that plan.)
- Axum / Actix — backend is Rocket.
- Plain `Secret` resources committed to git — always go through Sealed Secrets (kubeseal). `infra/k8s/base/secrets.example.yaml` shows the shapes but is reference-only.
- Bypassing ArgoCD by running `kubectl apply` against the cluster — ArgoCD will revert it on the next sync. Make changes in git.
- Pinning images to `:latest` in overlays — the build-and-deploy workflow pins to `:<branch>-<sha>` immutable tags.

## System Design Highlights

### Sky-Camera Platform (Skycam)
A real-world IoT → cloud pipeline built end-to-end: Raspberry Pi captures all-sky images → Rust/Rocket microservice ingests FITS + JPEG + telemetry → S3/MinIO storage + MongoDB metadata → React GUI + cloud-detection worker.

**Key architecture decisions:**

1. **Two-tier cadence** (preview every 2s, FITS every 60s)
   - Problem: limited bandwidth (school WiFi, cellular, satellite uplinks) + limited disk (Pi SD card).
   - Solution: lossless FITS at ~60s intervals; lossy JPEG previews at 2s for responsive UI + faster cloud-detection feedback. Settings `OBS_INTERVAL_S` and `OBS_FITS_INTERVAL_S` are env-driven per device.
   - Trade-off: adds complexity (two image paths) but necessary for real deployment constraints.

2. **Classical (non-ML) cloud detection** (star count + brightness + R/B ratio)
   - Problem: ML models require GPU, training data, and are opaque (unacceptable for observatory science).
   - Solution: physics-based heuristic: clear night sky → many point-source stars (detected via median-subtraction + blob analysis). Cloudy → occluded stars → high cloud_score.
   - Benefit: fast (ms-scale), explainable, calibratable on real data, portable to Pi.
   - Current: thresholds tuned on synthetic data; will refine on real night-sky observations.

3. **Poll-based detection** (Beat scheduler queries Mongo every 3s)
   - Problem: Pi + Celery workers are remote; event-driven push (LPUSH → broker) requires persistent connection or bridge.
   - Trade-off chosen: poll simplicity over push latency (3s scan interval is acceptable for sky monitoring).
   - Key asymmetry: polling is **self-healing** (a missed frame is picked up on the next scan); event-driven is not — a dropped event means a frame stays unscored forever with nothing to notice. Going event-driven therefore requires a reconciliation sweep + a DLQ, not just a broker.
   - **Decision (2026-10-01): polling stays. No `LISTEN/NOTIFY` listener will be built.** Earlier notes called a listener "next". That framed it as a latency upgrade without asking whether latency matters, and here it doesn't: clouds change over minutes, and acting on them (pausing, closing) takes minutes, so a 3s or even 30s delay changes no decision. The usual other argument, wasted database load, doesn't hold either: the partial index makes each poll a few-row index scan costing microseconds. A listener would add a process, a dedicated connection and the PgBouncer trap, and buy nothing a user notices. The Go service's `NOTIFY frame_ingested` stays; it is harmless and works through PgBouncer, since only `LISTEN` breaks there. **Interview line:** *"I considered event-driven, measured that polling was effectively free, and the domain doesn't need sub-second latency."* See **Detection cadence and transient events** below for the scaling work that does matter. Trade table + Mongo-worker defects: `CLOUD_DETECTION_AND_REDIS.md`.

4. **Presigned URLs for FITS, stable cacheable URLs for previews** (revised 2026-10-01)
   - Problem: GUI must read images; full API auth on every image load is chatty; need public CDN for fast preview access.
   - Original solution: presigned URLs for everything, pointing at `S3_PUBLIC_ENDPOINT`.
   - **What was wrong with it:** a presigned URL differs on every request, so no CDN or browser cache can reuse it. Every viewer pulled every preview from S3, and every `/frames` response was unique and uncacheable.
   - **Now:** previews at `GET /skycam/frames/<id>/preview.jpg`, `immutable` for a year (written once, never changes). The live view polls one `GET /skycam/live` with `max-age=2, stale-if-error=60`. FITS stays presigned: large, rarely fetched, not worth caching. Measured at 2,000 viewers: ~47 origin requests in 30 s, against ~14,400 for 500 viewers with no cache. See SCALING.md, "Live view", including the SSE comparison.
   - Learned: presigned URLs are right for private, rarely fetched objects and wrong for hot public ones. Previews were never secret (the read API is unauthenticated), so the URLs bought no security and cost all caching.

5. **Per-device settings synchronization**
   - Problem: camera config (gain, exposure, filter) must be adjustable from GUI but applied on Pi.
   - Solution: Pi fetches settings once per capture cycle (`refresh_settings()` in `run_once()`, so every 2s at the default `OBS_INTERVAL_S` — the 1s `OBS_SETTINGS_INTERVAL_S` throttle never binds; ~43,200 req/day). Fetch happens immediately before capture, so a change applies at the next capture. Server stores in MongoDB (device_id → settings doc). Decoupled pull model avoids connection state management.
   - GUI: embedded sliders in Live View → PUT /skycam/settings/{device_id} → Pi picks up on next poll.

### DevOps + Local Dev
- **Docker layer caching + WSL2 tuning**: Rust compilation is memory-heavy. WSL2 default (8GB) OOMs on aws-sdk-s3 deps. Fixed via `~/.wslconfig` (20GB RAM, 16GB swap). Docker layers cached; rebuilds now ~5s.
- **Sealed Secrets + ArgoCD**: Ingest token, S3 keys encrypted in git; no plaintext secrets anywhere. ArgoCD is source of truth; never kubectl apply directly.
- **CI/CD immutable tags**: Every commit → GitHub Actions build → GHCR push with `<branch>-<sha>` tag → kustomize overlay bumped → ArgoCD syncs. Rollback is one line: revert commit + re-push.

## Open Issues & Pending Decisions

### Known defects (fix before any DB migration, so it's measured against a fair baseline)
- **Indexes — FIXED 2026-09-30.** `skycam::db::ensure_indexes` creates five at startup, idempotently, and logs rather than crashes on failure (every query is still correct without its index, only slower, so refusing to start would turn a performance problem into an outage). `frames{captured_at:-1}` and `telemetry{recorded_at:-1}` serve the read API; `settings{device_id}` **unique** exists for correctness (concurrent upserts could create two settings docs for one camera); `frames{cloud_score:1}` serves the detect scan — a plain index, because MongoDB rejects `$exists:false` in a `partialFilterExpression`, and a missing field indexes as null; `alarms{frame_id,kind}` **unique**, with `detect/tasks.py` switched from `insert_one` to an upsert with `$setOnInsert` so a redelivered task no longer raises on it.
  - **Measured:** every read-API query went from `SORT <- COLLSCAN` to `LIMIT <- FETCH <- IXSCAN` with no sort stage. At 500k frames the latest-frame query went from **271 ms to 2 ms**, docs examined 500,000 → 1.
  - **Correction to earlier notes:** the old claim that the unindexed sort would "exceed the 32MB blocking-sort limit and error" was wrong. `find_one().sort()` is a top-k sort holding one document, and Mongo 7 spills to disk by default. The real defect was the `COLLSCAN`: every 3-second poll read every document, forever, linearly worse as data grew.
  - **Still open:** timestamps are stored as **strings**, not BSON dates (`DateTime<Utc>` with plain serde), and in **mixed formats** — `…Z` and `…+00:00`, with 6 or 9 fractional digits. Ordering is correct across seconds because the prefix differs first; within one second it can misorder. The real fix is `bson::serde_helpers::chrono_datetime_as_bson_datetime` plus a one-off migration of existing docs.
- **S3/MinIO retention — FIXED 2026-10-01.** There were no lifecycle rules, and the 100 GiB MinIO volume (shared by dev, release and prod) would be filled by **one camera in under 3 days** (~36 GB/day of FITS), after which every upload fails, including `releases/`. `minio-bucket-init` now installs prefix-filtered rules: `frames/` 1 day, `previews/` 7 days, abandoned multipart uploads 1 day (`FITS_EXPIRE_DAYS`, `PREVIEW_EXPIRE_DAYS`, `UPLOAD_RESUME_DAYS` on the Job). Verified against a real MinIO: prefix filtering (only `frames/` and `previews/` deleted; `releases/`, `datasets/`, `framesX/` kept), the real script run twice (idempotent), and two traps: **MinIO rejects an abort-only rule and silently drops `AbortIncompleteMultipartUpload` from a combined one**, so the Job sets MinIO's `stale_uploads_expiry` to match and verifies the stored rules, failing loudly if they're missing. The Go ingest's comment already assumed such a rule existed; `internal/blob/lifecycle_test.go` now proves a camera recovers when its half-finished upload is aborted (fresh upload, byte-identical result). The Rust preview route returned **502 + ERROR** for an expired object; it now returns 404. **Not solved by lifecycle:** the volume holds only a day or two of FITS for one camera. Cadence, compression and clear-sky-only retention are the real levers. Told as a challenge story in `SKYCAM_WRITEUP.md` §9.6.
- **Keep FITS only for clear sky, compressed — BUILT 2026-10-02 (Postgres pipeline).** Migration `0006_fits_archive` (a separate `fits_archive` table; `frames` untouched) + `detect/fits_archive.py` + tasks `scan_archive`/`archive_fits` (Beat every 60 s, `DETECT_ARCHIVE_CLEAR_FITS`, `FITS_COMPRESSION=GZIP_2|RICE_1|none`, `DETECT_ARCHIVE_WINDOW_S`=20 h, must stay under `FITS_EXPIRE_DAYS`). Only frames scored `is_cloudy = false` are claimed (insert-to-claim on the archive row's PK, so concurrent pollers are disjoint); raw bytes are SHA-256-checked against the upload before archiving; output goes to `archive/frames/<device>/<id>.fits.fz` with its own lifecycle rule (`ARCHIVE_EXPIRE_DAYS`=7). **Lossless is enforced, not assumed:** every result is decompressed and compared pixel- and header-exact, else the original bytes are stored (`compression='none'` + reason). **Measured on the real camera FITS: GZIP_2 2.07–2.25×** on unsaturated frames, exact round trip; **all 82 real FITS in the dev bucket are daylight/dusk, many saturated — still no real night data.** 26 new tests (53 in the detect suite), and the deployment rehearsal confirmed the Beat → worker wiring. The fake Pi's FITS are pure noise, so they archive uncompressed by design. **Legacy Rust/Mongo path unchanged:** there, raw FITS simply expire after a day. **Next:** compress on the Pi (Rice, cheaper CPU) to save *uplink* bandwidth, the original constraint; this server-side step only saves storage.
- **Poison-pill loop.** In `detect_frame`, the no-preview path writes a `None` sentinel but the error path doesn't — a frame that fails S3 fetch or `cv2` decode is re-enqueued every 3s forever. At `SCAN_LIMIT=50`, fifty bad frames starve out every real one.
- **Alarm writes aren't idempotent.** Plain `insert_one` on `alarms`; with `task_acks_late=True` a worker dying mid-task redelivers and writes a duplicate alarm. Reachable today, routine under any at-least-once broker.

### Detect worker (Celery/Redis) — Postgres backend BUILT + TESTED 2026-09-27; Mongo backend unchanged
`DETECT_BACKEND=mongo|postgres` picks the pipeline (same switch shape as `TELEMETRY_BACKEND`, and for the same reason: both must run side by side before the old one is removed).

**Postgres path (`tasks_pg.py` + `store_postgres.py`, migration `0003_detection`)** — the three known defects are fixed *structurally*: failures are **classified** (no preview → `skipped`, undecodable JPEG → `failed` immediately, S3 error → retried on a budget in `frames.detect_attempts`), `claim_pending` uses `FOR UPDATE SKIP LOCKED` so two pollers can never hand one frame to two workers, and alarms use `ON CONFLICT (frame_id, kind) DO NOTHING`. A `reclaim_stale` sweep returns claims whose worker died, dead-lettering them as `failed` + `detect_error` once the budget is spent — the DLQ is a row state, not a second queue, so "why did this never score" is answerable in SQL. `frames` also now stores `star_count`/`brightness`/`rb_ratio` so thresholds can be recalibrated without re-reading every JPEG.

**Verified:** 27 tests against real Postgres + MinIO + Redis (no mocks; one asserts `EXPLAIN` still uses the partial index), then end to end — 64 frames uploaded by the fake Pi through Go ingest, all scored 0.0–0.95, 2 alarms raised, 0 errors, 0 retries. **Polling stays the primary trigger**: it is self-healing, and the partial index `frames_pending_detect_idx` makes it an index scan over the few pending rows. The real defect in the Mongo version was the *missing index*, not polling. No listener will be built (decision 2026-10-01, see Key architecture decision 3).

**Mongo path (`tasks.py`)** — untouched, still has all three defects below. The Postgres path is packaged for deploy (2026-09-30): `detect/Dockerfile` and a worker + Beat in `infra/k8s/components/skycam-v2` (dev only), rehearsed with 20 frames all scored. The Mongo path is not packaged and will not be.

| Concern | `mongo` backend | `postgres` backend |
|---|---|---|
| Celery app, Redis broker/backend | ✅ | ✅ (shared) |
| `acks_late`, `prefetch_multiplier=1` | ✅ | ✅ (shared) |
| `detector.py` + unit tests | ✅ | ✅ (shared, unchanged) |

| Deployment | ❌ `detect/Dockerfile`, kustomize entry, Redis manifest — **runs in no cluster env** | ❌ same |

What survives the migration: `detector.py`, the worker pool, retries, DLQ, idempotency.
What gets rewritten: only the store calls. The trigger stays a poll, now an index scan over pending rows rather than a collection scan.

### Auth — JWT + per-device RBAC BUILT IN GO 2026-09-28; Rust side still open
**Built (`services/ingest`, migration `0004_auth`).** `users` + `device_grants(user_id, device_id, role)` with `viewer < operator < admin`; the composite PK *is* the hot-path index. The control API accepts a user JWT or the legacy shared operator token (now explicitly a service account). CLI: `ingest user add`, `ingest grant add|revoke`.

Design points worth repeating: **authentication and authorization are separate** — a validly signed token for an unprovisioned subject gets `PermissionDenied`, and nothing about permissions rides *in* the token, so a revoked grant bites on the next request rather than at token expiry. **Ed25519, public key only** on the verifier (`INGEST_JWT_PUBLIC_KEYS=kid=<base64 PEM>,…`) — the `api` crate is the sole issuer; a shared HMAC secret would let any verifier mint tokens. Multiple `kid`s support rotation, and a `kid` is required once more than one key exists. **Authorization runs before payload validation and before the session lookup**, so an unauthorized caller learns neither the valid gain range nor which devices exist/are online; `ListConnectedDevices` filters rather than errors. Fixed on the way: `settings_audit.changed_by` now records the real user instead of the literal `"operator"`.

**Verified:** 16 JWT tests (incl. `alg:none` and HS256-signed-with-the-public-key), 12 authorization tests against real Postgres, and a load test at **100 users (1570 req/s) and 500 users (1663 req/s, p50 333ms)** where every user also attempts a write to a neighbour's camera — **zero unauthorized writes succeeded**, and every camera was read back to confirm it never held the trespass value. `AccessFor` benchmarks at **122µs**, so authorization is ~0.04% of request latency; the ceiling is the pgx pool (8 conns default). Raising it to 32 gave +37% throughput (→2271 req/s); 64 gave ~nothing and worsened p99 — queueing just moves into Postgres. **`-race` first run 2026-09-30** (in a `golang:1.27` container, since this machine has no gcc): whole suite, **0 races**; the two load tests are excluded under race for memory. CI now runs it on every push (`skycam-ci.yml`).

**Sign-in (OAuth 2.0 code + PKCE) BUILT 2026-09-28** — `internal/oidc` + `internal/authsvc`, a third HTTP listener (`INGEST_AUTH_ADDR`) serving `/auth/login`, `/auth/callback`, `/auth/me`. Confidential client (exchange is server-side with the secret; the browser never sees a provider token), PKCE on top because it defends against an intercepted code and a client secret does not. **Three values, three jobs, none substitutes for another:** `code_verifier` (intercepted code, checked by the provider), `state` (CSRF, single-use, ours), `nonce` (ID-token replay, ours). `S256` only. Identity is the **subject**, never email; unverified email refused; `return_to` on an exact allow-list and rejected *before* any state is stored. The provider's ID token is consumed once and exchanged for our own Ed25519 token — our expiry, our key, no runtime dependency on Google. `AutoProvision=false` by default, so anyone can authenticate but only provisioned users get in. `ingest keygen` prints the keypair as env vars. **Multi-replica: solved 2026-09-30.** `oidc.RedisFlows` (`SET NX EX` + atomic `GETDEL`) is used whenever `INGEST_REDIS_URL` is set; the in-memory `Pending` remains the single-replica default. Tested: the full browser flow behind a round-robin balancer over two instances passes, and the in-memory store fails the same test (the control); 60 racing callbacks on 3 pods → exactly one sign-in. A Redis outage returns 500, not "start again".

**Verified:** 7 PKCE/state tests + 16 sign-in flow tests against a **stub IdP that enforces PKCE itself** — a code redeemed with the wrong verifier is refused, with a control test proving the right one succeeds. Plus one test that mints with the real `Issuer` and calls gRPC with it, closing the issuer↔verifier loop (they're configured separately, so a kid/audience mismatch would break every sign-in while both sides' own tests passed).

**Per-caller rate limiting BUILT 2026-09-29** — `internal/ratelimit`, a token bucket per authenticated caller, applied in the interceptor *after* auth because the meaningful key is the device/user, not the IP (every camera arrives through one Cloudflare tunnel, so an IP limit throttles the fleet or nothing). **Token bucket over fixed window** because a camera draining its spool after an outage is *legitimate* burst traffic, and because a fixed window lets a caller send 2× the limit across a boundary — there is a test asserting that boundary case. Defaults from measured cadence (~0.6 req/s per camera): `INGEST_DEVICE_RPS=2`, `BURST=60`; operators 20/100; `0` disables. A stream costs one token **at open**, not per message, so a chunked 25MB upload can't throttle itself. Returns `ResourceExhausted` (not `Unavailable`, which tells clients to retry immediately). Non-blocking. The shared operator token is exempt (platform talking to itself over loopback). Idle buckets evicted, but a *draining* bucket is kept so a caller can't clear its debt by going quiet. **17 tests.** **Multi-replica: solved 2026-09-30.** `ratelimit.RedisLimiter` runs the same bucket as one Lua script (atomic), on Redis's clock not the pod's, with a key TTL equal to the refill time so expiry only forgets buckets with no debt. **Fails open** when Redis is down. Tested: two replicas → exactly one burst, where the in-process limiter (control) allows two; 200 concurrent requests on 4 replicas → exactly the burst; the same over real gRPC with two servers. One comment was wrong on the way and a mutation test caught it: Redis does not truncate Lua numbers passed as *arguments* (only return values), so the `tostring()` guard was removed. `tostring` keeps only 14 significant digits, which is worse.

### Cross-replica command routing — BUILT 2026-09-30
`internal/cluster` (Redis pub/sub + expiring presence key), enabled by `INGEST_REDIS_URL`. Removes the Tier-1 blocker in `SCALING.md`: a second replica could not reach a device whose stream another pod held. **Two features, two jobs** — `SET session:<device> = <replica> EX 30` answers *where* (pub/sub can't tell you if anyone listened, and the TTL expires a crashed replica's claim without a sweeper), `PUBLISH cmd:<device>` delivers, `PUBLISH ack:<replica>` returns the ack demultiplexed by command id. Lossy pub/sub is acceptable **only** because the proto already treats commands as best-effort-right-now and `SendCommand` already reports *sent but unacknowledged*; everything durable stays in Postgres. Unreachable-but-configured Redis is fatal at startup rather than silently degrading. `ListConnectedDevices` now spans replicas.

**Three ordering bugs the tests found, each now documented in code:** subscribe *before* announcing (else a command lands on the stale replica); **presence is authoritative even when a local session exists** (a moved device leaves a stale session for up to the 90s idle timeout, and trusting it sends commands into a dead stream); and register for the ack **per command id** before publishing (one shared channel with several readers meant waiters consumed each other's acks). **20 tests** — 13 on the bus, 7 spinning up two real gRPC servers sharing one Postgres and one Redis, including a device that moves replicas mid-flight and four concurrent cross-replica commands.

### Rain alerting — BUILT + TESTED 2026-09-30 (`notify/`)
Third-party forecast (Open-Meteo, batched multi-coordinate) → rules → `alerts` → coalesced email. Migration `0005_notifications`. **Nothing in this platform can predict rain** — `detector.py` counts stars, which is current cloudiness and night-only — so the forecast is necessarily external. **An alert is a row, not a message:** pub/sub can't retry, be acknowledged or be audited, and silent loss is the one unacceptable failure here; Redis is only the Celery broker. **Its own queue** (`-Q notify`), because sharing detection's would put thousands of frame-scoring tasks in front of a time-critical alert.

**Scale-first decisions:** the schedule lives in `forecast_sites.next_poll_at` claimed with `SKIP LOCKED`, so staggering, per-site backoff and the staleness check fall out of the claim query **and a duplicated Beat becomes a no-op** (which is why Beat is fine here); devices group by rounded coordinates so 200 sites are a handful of batched calls rather than 28,800/day against a ~10k free tier; hysteresis (fire 0.55 / clear 0.30) stops flapping; `alerts.fingerprint` unique index stops a re-evaluated forecast emailing twice; hard bounces mark an address undeliverable because retrying wrecks the sending domain and then *nobody* gets mail; `check_staleness` exists because no alerts looks exactly like good weather.

**Verified: 35 tests**, and **200 sites / 50 users → 4 provider calls, 50 emails** (4× coalescing). Two real bugs found: the claim batch was counted in *deliveries*, which gave every user two emails at 200 sites (the unit of work is an email, so it counts users); and the site key was computed in **both** Python and SQL, which disagreed on negative zero (`0.00` vs `-0.00`) so a camera at a small negative longitude never matched its own site — fixed by a generated column as the single definition plus positional provider results. **Packaged 2026-09-30** (`notify/Dockerfile`, worker + Beat in the dev component), but it cannot mail real users yet: no bounce webhook, no canary, and SES must leave sandbox (1/s, 200/day) first.

**Still open (Rust side).** `PUT /skycam/settings` in the Rust service remains unauthenticated (`backend/crates/skycam/src/routes/settings.rs`) — anyone who can reach it can change exposure/gain on a live camera. Google sign-in and token *issuance* don't exist yet; the Go service verifies tokens nobody mints. Per `README.md` the issuer is the `api` crate and **JWT verification belongs in the `domain` crate** so `api` and `skycam` don't duplicate it. Browser → Rust (verify JWT, check grant) → Go control service is the intended path, since the control listener is loopback-only.

### Detection cadence and transient events — PROPOSED 2026-10-01, not built
The question that settles most design choices here: **how fast does the thing being detected actually change, and what does a person do about it?** Capture cadence, analysis latency and analysis coverage are three different dials, and each job sets them differently.

| | Cloud detection | Transient detection (meteors, satellites) |
|---|---|---|
| Frames analysed | **A sample**, ~1 per device per 30–60s. The sky changes over minutes | **Every frame**. Skip one and the event is gone |
| How fresh the result must be | Minutes is fine | Hours is fine. The use is review, catalogues, recovery |
| Where it runs | Server (today) | **On the Pi**, uploading only candidate events |
| Real risk | **False alarms**: planes, birds, dew | **Gaps between exposures**, JPEG losing faint streaks |

**Clouds: sample and debounce (the real scaling win).** Today every 2s preview is scored, about 100 frames/s of decode and star-counting at 200 sites, for near-identical consecutive scores. Sampling one frame per device per 30–60s cuts detection work roughly 15–30×. Then debounce: raise "cloudy" only when e.g. 3 of the last 4 samples agree, and clear at a lower threshold (the same hysteresis as rain alerts, fire 0.55 / clear 0.30). Store **one sky state per device** (clear / cloudy / unknown) rather than an alarm row per frame; that state is what the GUI and observers want.

**Meteors: completeness, not latency.** A meteor lasts under a second and nobody can act on it, so millisecond detection buys nothing. Capture is the constraint:
- **Gaps:** ~1s exposure every 2s means the camera is blind about half the time; a 0.5s meteor has roughly even odds of falling in a gap. Needs back-to-back exposures.
- **Quality:** previews are lossy JPEG and FITS is only every 60s, so most of the night has no lossless record.
- **Bandwidth:** lossless all night is ~36 GB per site. So detect **on the Pi** (frame-to-frame difference, new bright line) and upload only the event frames at full quality.
- **Where 200 sites pay off:** two or more cameras seeing the same meteor give its 3D path by triangulation (height, speed, orbit, fall zone). That needs **clock sync to a few ms** (NTP, ideally GPS) and per-camera sky calibration, plus a batch job matching events across sites. The milliseconds that matter are in the **timestamps**, not the detection.

**Telling users about meteors: the notify pipeline, not LISTEN/NOTIFY.** `LISTEN/NOTIFY` is fire-and-forget between database connections: no storage, no retry, no record of delivery. A user notification needs all three. So the same shape as rain alerts: Pi → gRPC event → event row → notify worker → email/push, retried, delivery recorded per user. *An alert is a row, not a message.* The hard problem is **volume**: ~100 meteors/hour at the Perseids' peak, so offer fireballs above a brightness threshold, a nightly digest, or shower-active notices, never one email per meteor. A live pop-up in an open GUI is a browser push (WebSocket/SSE) sent by the Go service as the gRPC event arrives, across replicas over the existing Redis pub/sub; still no `LISTEN`.

### U-Net cloud segmentation — blocked on data, not on modelling
Segmentation (*which region* of sky is clouded) is genuinely more useful to an observatory than one scalar score, since what matters is whether the target is clear. But:
- **Blocked on labels.** U-Net is supervised; it needs per-pixel masks. Current thresholds are tuned on *synthetic* data, so there isn't much real night data either.
- **Domain shift is the real risk.** A model trained on public datasets (SWIMCAT / SWINSEG — verify licensing and size) learned someone else's optics, sensor noise, and light pollution. It degrades on our Pi + fisheye, and fails *quietly* — confident, wrong masks. Worse than the heuristic being obviously night-only.
- **Viable path:** pretrain on public data, fine-tune on ~50–100 of our own labelled frames (transfer learning cuts the labelling need by orders of magnitude). LLM tools can write the training loop; they can't produce labelled frames from our camera or notice the model is wrong on our sky.
- **Gating action:** start collecting real night frames now — it's passive, and the current thresholds need the same data for calibration.
- **Cheaper win first:** the detector is night-only, so daytime frames all read as cloudy. The R/B-ratio branch is already sketched in `detector.py`'s docstring.

### MongoDB and DynamoDB — NEITHER IS PART OF THE SKYCAM DESIGN (clarified 2026-09-30)
Say this plainly, because the earlier notes read as if they were. **The new stack — Go ingest, `notify/`, `internal/cluster` — is Postgres + Redis + S3 end to end and touches neither.**

- **MongoDB is the incumbent, not a choice.** All three Rust services use it because it is what is deployed. Retire it at cutover: once the Go service ships, delete `detect/tasks.py` and flip `DETECT_BACKEND` to `postgres`. The switch exists only so both pipelines can run side by side during that cutover.
- **DynamoDB was an external directive**, platform-wide, motivated by ops burden (three self-managed Mongo StatefulSets), **not** by skycam performance. `TELEMETRY_BACKEND` defaults to `postgres`; the 593 lines of adapter execute nothing unless switched on. Telemetry at 200 sites is ~100 writes/s, which Postgres does not notice — DynamoDB buys skycam **zero** technically.

Keep the code (it costs nothing off, and it is the only migration evidence), but **never describe skycam as using DynamoDB.** An interviewer who reads the config will find the default and wonder what else was overstated. The defensible story is the scoping, not the migration: *a platform-wide directive was narrowed to the one collection that is genuinely DynamoDB-shaped, and moving `frames` was argued against because it would kill the transactional `NOTIFY`.* Declining part of a directive with a reason is the stronger signal.

### DynamoDB migration — platform-wide, driven externally
**BUILT AND RUN LOCALLY (2026-09-25) — see `DYNAMODB_TELEMETRY_MIGRATION.md`.** Adapter (`internal/store/dynamo.go`), dual-write (`TELEMETRY_BACKEND=postgres|dynamo|both`), and `cmd/migrate-telemetry` (backfill / verify / bench) all work: **669 real rows migrated out of `observatory_dev.telemetry` and verified**, re-run proven idempotent, dual-write and cutover demonstrated. **Against DynamoDB Local, not AWS** — no account, no cloud table, so the latency comparison that would decide anything hasn't been run. Scope: only `telemetry` (append-only, device+time-range access, no joins, highest write volume, lowest value per row; PK=device_id, SK=recorded_at ISO-8601, TTL retention). It is the one collection that is genuinely DynamoDB-shaped, it touches neither `frames` nor the detection pipeline, and `store.TelemetryStore` already exists so it is a second adapter, not a rewrite. Explicitly **not** `frames`: that would make the "blobs on S3, keys under the 400KB limit" line literally true but kills the transactional `NOTIFY` and forces a Streams-based detection trigger.
Not a skycam performance decision. Likely motivated by ops burden (three self-managed MongoDB StatefulSets, one per namespace). Consequences and the Streams upside are written up in `CLOUD_DETECTION_AND_REDIS.md`. Open questions for the decision-maker: what's driving it (cost / ops / broader AWS move), is the whole platform moving or just the DB, and what's the timeline. Scope note: all three Rust services use the `mongodb` driver, plus the Python worker — it's a rewrite of every data-access path in the workspace.
